## 2. Native Zen and control plane
- [x] 2.1 Extract shared normalization with conformance for merge, null, numeric, aliasing, errors and custom rules. `rust/zen-normalize` owns it and the core NIF calls it; its expected records were produced by the JSON-text implementation it replaced.
- [x] 2.2 Retain native values across rules and compile outside the hot path. A `RuleSet` is compiled once; records stay Zen variables between rules. Each rule still gets its own copy of the record's containers, because no test establishes that every node type leaves its context alone.
- [x] 2.1a Make `strip_full_message` remove the field. Nulling a top-level field removes nothing, because Zen deletes the null from the rule's result and the overlay keeps the old value. A rule now removes top-level fields by naming them in `serviceradar_remove_fields`; only the bundled `strip_full_message` rule does, and the seeder refreshes seeded copies that are not user-authored. No other rule changes behavior.
- [x] 2.2a Call the shared rule set from Flowgger with records built directly as Zen variables. `flowgger::normalized` builds the record JSON mode publishes as Zen variables, runs the active ruleset on the input thread and encodes the result as OTLP. On whenever the collector has a `[rules]` section, unless `[rules] normalize = false` or `LOG_COLLECTOR_NORMALIZE_SYSLOG=false`.
- [x] 2.3 Publish self-versioned effective rules through datasvc; reconcile rule scope. `ZenRuleSync` publishes one digest-identified bundle per stream and subject at `zen/rulesets/<stream>/<subject>.json`, built from the rule list core's normalizer also reads; `rust/zen-normalize` verifies and compiles it.
- [ ] 2.3a Publish a rule set too large for one KV value as immutable documents under a manifest. Today datasvc rejects it and the previous bundle stays. A published bundle was observed on the demo deployment on 2026-11-18: core's datasvc client listed ten bundle keys under `zen/rulesets/`. The manifest for oversized rule sets is still open.
- [x] 2.4 Implement bounded fetch/watch/reconnect, atomic activation, cold start, empty snapshots and invalid/stale updates. `ActiveRules` in `rust/zen-normalize` does activation, cold start, empty snapshots and invalid or stale updates. The log collector follows its bundle key through datasvc: fetch on every connect, watch, and reconnect at 1 to 30 seconds, with the chart and Compose granting it read access to `zen/rulesets/` only. It is deliberately not a readiness condition: a collector with no ruleset yet takes syslog and publishes it as JSON for EventWriter to normalize. Superseded by `refactor-collectors-onto-shared-ingest-pipeline`: that collector will instead publish a schema-header batch without `Sr-Ruleset-Id`, stored with built-in mapping. Observed on the demo deployment on 2026-11-18: each collector logged that it follows `zen/rulesets/events/logs.syslog.json` and activated the bundle by digest. When the datasvc pods were replaced during a rollout, the watch failed, the collector kept the active ruleset and said it may be stale, and it was following a new watch one second later.

## 3. Binary and consumers
- [ ] 3.1 Specify metadata fields and complete OTLP/JSON field parity. OTLP protobuf rows now fill observed_timestamp, trace_flags, event_name, source_ip and scope_attributes like JSON rows (#6699). The collector decides the columns OTLP has no field for (`source`, `source_ip`, the service columns) and the syslog wrong-clock time fallback, and sends the columns as `serviceradar.column.*` attributes that only its subject may set; only the collector and an edge leaf carrying an edge collector's batches may publish that subject. Shared cases in `rust/flowgger/tests/resources/normalized_log_parity.json` hold both paths to the same row. Still open: `serviceradar.record_id`, `serviceradar.source_id`, `Sr-Collector-Id`, `Sr-Normalization-Version` and `Sr-Routing-Epoch`, deferred until something reads them (routing is partitioned).
- [ ] 3.1a Decide whether Zen rules configured for `logs.otel` should apply to protobuf OTLP logs. Today they do not: protobuf is that subject's format and is stored without rules. Applying them means running Zen on every OTLP log.
- [x] 3.2 Implement byte/count/age batches with fixed retry bytes and one route/ruleset. The NATS output closes a batch at 256 records, 256 KiB or 100 ms by default, never mixes rulesets, and retries the bytes and message ID it first sent.
- [ ] 3.3 Adapt dual-format EventWriter consumption preserving all required side effects. EventWriter reads collector-normalized OTLP batches from `logs.normalized.<kind>` without running Zen again, requires `Sr-Log-Schema: otlp-normalized-v1`, records `Sr-Ruleset-Id` when the batch carries it, stores a schema-header batch without `Sr-Ruleset-Id` with built-in mapping, and never reads JSON there. Only collector identities, and the edge leaf that forwards an edge collector's batches, may publish that subject. Protobuf is refused on every other `logs.` subject except `logs.otel`, so switching format cannot skip a subject's rules. Stored-row parity with the producer is checked by the shared cases. Still open: promotion and service-catalog side effects compared on a deployment.
- [ ] 3.4 Verify persistence-before-ACK, partial failure/replay and StarRocks/CNPG parity.
- [ ] 3.5 Roll readers before opt-in producers; verify legacy retained-message draining. Readers shipped first: EventWriter has read `logs.normalized.syslog` since v1.5.6, and the collector started producing it by default only afterwards. On the demo deployment on 2026-11-19 the collector was switched over while JSON messages were still arriving; rows from both subjects were stored. Still open: a deliberate check that retained JSON messages drain after the switch.

## 4. Performance gates
- [ ] 4.1 Compare equivalent normalized data through Broadway and standalone Rust consumers.
- [ ] 4.2 Compare final warehouse JSON/CSV encoding and bounded load concurrency.
- [ ] 4.3 Record reproducible synthetic throughput/latency/cost evidence before selecting replacements.
- [x] 4.4 Before normalized syslog is enabled in a deployment, measure an EventWriter log flush at its largest: a normalized message holds up to 256 records, so one flush can reach about 32,768 rows on StarRocks (128 messages) or 25,600 on CNPG (100 messages). Inserts are already split by rows and bytes; record memory, flush time against the 120 s ack wait, and log promotion cost over that many rows. Measured on the demo deployment (CNPG log storage) on 2026-11-19 with synthetic syslog over TCP: 30,000 lines arrived as 118 normalized messages and were all stored, with no duplicates, within 15 seconds of the last line being sent, against the 120 s ack wait; core memory did not visibly move. A stored row matched the row the JSON path stores for the same line in every column. Not measured: the StarRocks flush (128 messages), which that deployment does not use for logs.

## 5. Test and measurement tooling
Hegel (`hegeltest`) for properties and Criterion for benchmarks, as the longshore project already uses them. Each is its own change.
- [x] 5.1 Keep the fraction of a second in stored log times. EventWriter reads a nanosecond time as whole seconds, so logs one sender wrote in the same second cannot be ordered. Fix it for logs on the OTLP, JSON and normalized paths without changing the shared `FieldParser`, which has 36 callers.
- [x] 5.2 Add `hegeltest` to the workspace and the vendored crate set, and confirm it runs hermetically on the remote executors.
- [x] 5.3 Hegel: for any decoded syslog record, the record the collector hands its rules equals the record JSON mode publishes.
- [x] 5.4 Hegel: for any sequence of records, rulesets and limits, the batches hold every record once and in order, never mix rulesets, and stay within the byte limit unless one record exceeds it; every batch decodes to exactly its records.
- [x] 5.5 Hegel: for any JSON object a rule can return, the row mapping produces a record without panicking.
- [x] 5.6 Hegel: for any sender time and receive time, the stored time is the sender's or the receive time, and the fallback attributes are present exactly when it is the receive time.
- [x] 5.7 Cross-language property: generated records and rule outputs store the same row through the collector and EventWriter paths. EventWriter's parity test runs the collector's generators (300 cases per run, 30,000 nightly). Its first run found the JSON path storing a different row, or raising, for about half of the generated cases; `ServiceRadar.EventWriter.LogRow` now makes each column decision the way the collector does.
- [x] 5.8 Criterion: normalize and encode one record with the bundled syslog rules, assemble a batch, and encode in JSON mode as the baseline. These give reproducible per-stage numbers that feed 4.1 to 4.3; they do not replace the end-to-end measurements those tasks and the design's rollout section require.
- [ ] 5.9 If 5.8 shows the per-record ruleset lock matters and it is replaced with a lock-free read, ship that change with a Loom model of activation racing readers. The first measurement (consolidate-log-collectors `performance.md`) puts the lock inside 7.4 µs of an 80 µs record, so it does not matter yet; rule evaluation does.
