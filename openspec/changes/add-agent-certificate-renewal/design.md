# Design: Automatic Agent mTLS Certificate Renewal

## Context

ServiceRadar edge agents authenticate to `serviceradar-agent-gateway` over outbound gRPC with mutual TLS (`mTLS`). During initial enrollment (`serviceradar-cli enroll --token <token>`), the agent fetches an encrypted onboarding bundle generated by `ServiceRadarWebNG.Edge.OnboardingPackages` and `ServiceRadarAgentGateway.CertIssuer` (or `ServiceRadar.Edge.OnboardingPackages`), writes `component.pem`, `component-key.pem`, and `root.pem` to `/etc/serviceradar/certs/`, and starts `serviceradar-agent`.

The following describes the pre-implementation defects that motivated `#6120`:
1. **Accidental 1-day default lifetime**: `ServiceRadar.Edge.OnboardingPackages.create_with_platform_cert/2` defaulted `:cert_validity_days` to `1` while `ServiceRadarAgentGateway.CertIssuer` defaulted to `365`. Packages created without an explicit `:cert_validity_days` option minted leaf certificates that expired 24 hours after enrollment.
2. **No renewal path**: Neither the Go agent (`go/pkg/agent`, `go/pkg/grpc/security.go`) nor `monitoring.AgentGatewayService` (`proto/monitoring.proto`) has a certificate renewal RPC, background rotation timer, or dynamic TLS certificate reload callback (`GetClientCertificate`).
3. **Opaque failure and zero inventory visibility**: `platform.ocsf_agents` does not record certificate expiration (`notAfter`), serial number, or fingerprint; SRQL cannot query expiring agents (`in:agents cert_expires_at:<7d`); and when the certificate expires, the agent reports `rpc error: code = DeadlineExceeded desc = context deadline exceeded` while the gateway emits a bare Erlang `:ssl` alert (`bad_certificate` / `certificate_expired`) without mapping it to the affected `agent_uid`.

Additionally, `#5413` removes all SPIFFE/SPIRE infrastructure from the repository, and `#5257` requires durable revocation for edge leaf and component certificates. The renewal architecture must operate strictly on ServiceRadar's internal X.509 CA and integrate directly with `#5257`'s revocation model.

## Goals / Non-Goals

### Goals
- Provide zero-touch, in-band mTLS leaf certificate renewal for connected agents before certificate expiration.
- Enforce fresh key generation and cryptographic proof of possession on every renewal while binding the issued certificate strictly to the authenticated peer identity.
- Support atomic on-disk persistence and zero-downtime hot reload of renewed certificates in the Go agent (`GetClientCertificate` / `GetCertificate`).
- Define an explicit threat model and recovery procedure for agents whose certificates have already expired while offline.
- Eliminate the 1-day default validity trap and make leaf certificate lifetimes explicit and configurable.
- Expose per-agent certificate lifecycle metadata (`cert_expires_at`, `cert_serial_number`, `cert_fingerprint_sha256`, `cert_last_renewed_at`, `cert_renewal_error`) across CNPG (`ocsf_agents`), SRQL (`in:agents`), the Web-NG Fleet UI, and the alerting engine.
- Unify renewal predecessor retirement and administrative revocation with `#5257`.

### Non-Goals
- Depending on SPIFFE/SPIRE, SPIRE Workload API, or external ACME CAs for agent-to-gateway mTLS.
- Automatic rotation of the platform Root CA (`root.pem`) itself (Root CA bundle distribution uses a multi-root trust bundle in `root.pem` across releases, covered separately from leaf rotation).
- Accepting expired certificates over an unauthenticated renewal endpoint.

## Decision 1: Issuance Authority and In-Band Renewal Protocol

### Issuance Authority
`ServiceRadarAgentGateway.CertIssuer` (signing with the deployment's internal CA keypair mounted at `/etc/serviceradar/certs/root.pem` + `root-key.pem` or the configured `CA_CERT_FILE` / `CA_KEY_FILE`) is the sole issuance authority for edge component leaf certificates.

To prevent identity spoofing if a CSR contains forged subject or SAN fields:
1. The renewal RPC (`AgentGatewayService.RenewCertificate`) runs on the existing mTLS-authenticated gRPC server (`ServiceRadarAgentGateway.AgentGatewayServer`).
2. The gateway extracts the caller's DER client certificate from the active gRPC transport (`GRPC.Stream.get_cert/1` / peer certificate metadata) and resolves `%{component_id, partition_id, component_type, certificate_fingerprint, serial_number}` via `ServiceRadarAgentGateway.ComponentIdentityResolver.resolve_from_cert/2`.
3. `ComponentIdentityResolver` checks `ServiceRadarAgentGateway.AgentCertificateRevocation.revoked?/1` before the RPC handler proceeds. If the current certificate or `component_id` is revoked, the renewal call is rejected with `PERMISSION_DENIED` (`certificate_revoked`).
4. The gateway verifies the client's PKCS#10 CSR signature over the DER-encoded `CertificationRequestInfo` using the public key from the CSR's `subjectPublicKeyInfo` and its supported signature algorithm (`:public_key.verify/4` or equivalent) to prove possession of the newly generated private key, enforces supported key strength (ECDSA P-256/P-384/P-521, Ed25519, or RSA >= 2048 bits), and rejects mismatched Subject CN or SANs with `csr_identity_mismatch`. Certificate identity fields are constructed from the authenticated peer, not copied from the CSR.
5. Immediately before signing on every `RenewCertificate` attempt, the gateway checks the authenticated transport peer certificate against its current UTC time, requiring `NotBefore <= now < NotAfter`, including on an existing TLS connection and after any issuance wait. It rejects an expired peer with `PERMISSION_DENIED` (`certificate_expired`) and a not-yet-valid peer with `PERMISSION_DENIED` (`certificate_not_yet_valid`), without issuing a successor. Handshake-time validation does not authorize later renewal attempts.
6. `CertIssuer.issue_from_csr/5` signs the new leaf certificate through OpenSSL using the CSR's `subjectPublicKeyInfo` and the server-derived `component_id`, `partition_id`, and `component_type`:
   - Subject CN: `<component_id>.<partition_id>.serviceradar`
   - URI SAN: `spiffe://serviceradar.local/<component_type>/<partition_id>/<component_id>`
   - DNS SANs: `<component_id>.<partition_id>.serviceradar`, `<component_id>.serviceradar`, `localhost`
   - Extended Key Usage: `serverAuth`, `clientAuth`

### Protobuf Contract (`proto/monitoring.proto`)
The RPC and request/response fields are defined in [proto/monitoring.proto](../../../proto/monitoring.proto). Generated Go and Elixir bindings follow that schema.

The gateway derives current certificate metadata for inventory and audit correlation exclusively from the authenticated TLS peer certificate, including on `Hello` before the first renewal. `AgentHelloRequest` requires no certificate metadata fields.

### Renewal Schedule (`~2/3` of Lifetime)
The implemented schedule, retry delays, expiry recovery, and operator limitations are documented in [certificate operations](../../../docs/docs/edge-agent-onboarding.md#automatic-leaf-certificate-renewal). The renewal manager sleeps until the computed target or retry deadline. Reporting `cert_renewal_error` through `PushStatus` / `Hello` remains pending.

### Atomic Disk Write and Hot Reload
1. **Keypair Generation & Staging**:
   - The agent generates a new private key in memory; disk staging begins only after validating the renewal response.
   - It calls `AgentGatewayService.RenewCertificate` with the DER CSR.
   - Upon receiving `CertificateRenewalResponse`, the agent parses the leaf certificate, verifies that the public key matches the staged private key, verifies the signature chain against `ca_chain_pem`, and verifies `NotAfter > now`.
   - It writes and fsyncs the private key to `/etc/serviceradar/certs/.component-key.pem.tmp` with mode `0600` and writes the leaf certificate to `/etc/serviceradar/certs/.component.pem.tmp` with mode `0644` (`fsync` file).
2. **Atomic Commit**:
   - To prevent a power loss or crash between two `rename(2)` syscalls from leaving `component.pem` and `component-key.pem` mismatched, the agent writes a combined bundle `/etc/serviceradar/certs/.component-bundle.pem.tmp` (containing both the certificate chain and private key, `0600`, `fsync`), atomically renames it to `component-bundle.pem`, and `fsync`s `/etc/serviceradar/certs/` before replacing either live file. Only then does it atomically rename `.component-key.pem.tmp` -> `component-key.pem` and `.component.pem.tmp` -> `component.pem` and `fsync` the directory again.
   - On startup, if loading the certificate/key pair fails (for example, from an interrupted mid-rename crash) and `component-bundle.pem` is valid, the loader self-heals `component.pem` and `component-key.pem` from the durably published `component-bundle.pem` before loading TLS credentials. Repair writes and fsyncs temporary files, renames them over the live pair, and fsyncs the directory while retaining the recovery bundle, so an interrupted repair can be repeated.
3. **Zero-Downtime Hot Reload (`go/pkg/grpc/security.go`)**:
   - Replace static `tlsConfig.Certificates = []tls.Certificate{cert}` in `MTLSProvider` with an atomic pointer (`atomic.Pointer[tls.Certificate]`) backing `tlsConfig.GetClientCertificate` and `tlsConfig.GetCertificate`.
   - When the atomic disk write completes, `GatewayClient.ReloadAndReconnect()` calls `MTLSProvider.Reload()` to swap the in-memory `tls.Certificate` pointer, then reconnects the gateway gRPC channel; the renewal manager invokes enrollment (`Hello` + `ControlStream`) so the gateway immediately observes the new certificate serial/fingerprint and retires the predecessor certificate.

## Decision 2: Expired-Certificate Path and Threat Model

### Options Considered

#### Option A: Bounded Expired-Certificate Grace Window (Rejected)
Allow `serviceradar-agent-gateway` to accept an expired client certificate for `RenewCertificate` within a grace window (e.g., 7 days past `notAfter`) by using a custom Erlang `:ssl` `verify_fun` that ignores `{:bad_cert, :cert_expired}` on the TLS listener or on a dedicated renewal port.

**Threat Model Analysis of Option A**:
- **Weakens certificate expiration semantics**: A core security property of finite X.509 lifetimes is bounding the exposure window of an unrevoked key on a decommissioned laptop, RMA'd appliance, VM snapshot, or stolen backup. If a grace window allows an expired certificate to mint a fresh 90-day certificate, the effective compromise window of every certificate silently extends by the grace period.
- **TLS listener blast radius**: In Erlang `:ssl`, client certificate verification happens during the TLS handshake before HTTP/2 and gRPC method routing (`:path` is encrypted until the handshake finishes). Allowing `{:bad_cert, :cert_expired}` in `verify_fun` on port `50052` would admit expired certificates into the TLS session for *all* gRPC services unless every downstream RPC handler and interceptor duplicates expiry enforcement, creating a high-risk fail-open surface.
- **Does not solve long offline periods**: An appliance powered off on a shelf for 30 days still misses a 7-day grace window and requires re-enrollment anyway.

#### Option B: Re-Enroll Only on Expired Certificate, Paired with Single-Command In-Place Re-Enrollment (Recommended)
Once `now >= NotAfter`, `serviceradar-agent-gateway` strictly rejects the TLS handshake. An expired certificate CANNOT authorize `RenewCertificate`, even on a TLS connection established before expiry: the gateway rechecks `NotBefore <= now < NotAfter` immediately before signing every attempt.

**Why Option B is Recommended**:
- With a 90-day default lifetime and automatic renewal starting at day 60 (a **30-day renewal window** before expiry), an agent that connects during its final 30 days can renew automatically if issuance succeeds before expiry.
- Hosts offline throughout the renewal window, hosts with persistent renewal failures, and hosts caught by the legacy 1-day default bug can reach expiration and require re-enrollment.
- Preserves strict TLS handshake rejection (`verify_peer`, fail-closed on `:cert_expired`) with zero custom `:ssl` expiry bypasses.
- To make recovery painless for operators when a host was powered off past expiry, Web-NG and `serviceradar-cli` provide an **in-place re-enrollment token** flow:
  - In Web-NG Agents UI (or `POST /api/admin/agents/:uid/reissue-enrollment-token`), an administrator clicks **Re-enroll Agent** on an expired agent.
  - The control plane creates an `OnboardingPackage` pre-bound to the existing `component_id` (`agent_uid`) and `partition_id`, mints a new certificate via `CertIssuer`, and revokes the expired certificate's serial/fingerprint.
  - Running `sudo serviceradar-cli enroll --token <token>` on the host overwrites `/etc/serviceradar/certs/component.pem` and `component-key.pem` and restarts `serviceradar-agent`, resuming under the **exact same `agent_uid`** with all checker assignments, plugin assignments, and historical telemetry preserved.

## Decision 3: Explicit, Configurable Certificate Lifetimes (Fixing the 1-Day Default)

### Root Cause of the 1-Day Default
- `ServiceRadarAgentGateway.CertIssuer` previously defined `@default_validity_days 365` and `@max_validity_days 825`.
- `ServiceRadar.Edge.OnboardingPackages.create_with_platform_cert/2` (`elixir/serviceradar_core/lib/serviceradar/edge/onboarding_packages.ex:509`) had:
  ```elixir
  cert_validity = Keyword.get(opts, :cert_validity_days, 1)
  ```
- Any code path or test helper calling `create_with_platform_cert/2` without `:cert_validity_days` issued a 1-day leaf certificate.

### Design Fix
Phase 1 implements the shared `ServiceRadar.Edge.CertificateLifetimePolicy`.
See [certificate operations](../../../docs/docs/edge-agent-onboarding.md#certificate-lifetime-and-expiry-alerts)
for the current issuance bounds and overrides.

The deployment override and Web-NG package form are implemented as described
in the certificate operations guide above. Agreement across core-elx, web-ng,
and the agent-gateway is essential: web-ng resolves the lifetime it requests,
and the gateway compares the request against its runtime default to decide
whether long-TTL admin approval is required.

## Decision 4: Visibility, SRQL Support, Alerting, and Diagnostics

### CNPG Schema & Ash Resource (`ServiceRadar.Infrastructure.Agent` / `platform.ocsf_agents`)
Phase 1 stores the nullable certificate lifecycle columns defined by
`20261028120000_add_agent_certificate_lifecycle_columns.exs`; the Ash `Agent`
resource maps those columns. Hello and heartbeats persist peer metadata, with
replacement observation semantics described in [certificate operations](../../../docs/docs/edge-agent-onboarding.md#certificate-lifetime-and-expiry-alerts).
`cert_renewal_error` remains future work. Issuance does not update the active certificate inventory; authenticated peer observations do.

### SRQL Query Support (`rust/srql/src/query/agents.rs`)
The implemented fields, aliases, and relative comparisons are documented in the
[SRQL language reference](../../../docs/docs/srql-language-reference.md#agent-certificate-fields).
Renewal-error projection remains pending with `cert_renewal_error` reporting.

### Proactive Alerting
Phase 1 implements the expiry worker; its cadence, thresholds, and resolution
behavior are documented in [certificate operations](../../../docs/docs/edge-agent-onboarding.md#certificate-lifetime-and-expiry-alerts).
Immediate renewal-failure alerts remain pending with `cert_renewal_error` reporting.

### Explicit Connection Error Diagnostics
1. **Agent-side pre-flight and handshake error classification (`go/pkg/grpc/security.go` & `go/pkg/agent/`)**:
   - Before each renewal attempt or retry, before dialing `serviceradar-agent-gateway`, and inside `GetClientCertificate`, the Go agent checks the local leaf certificate's `NotAfter` against `time.Now()`.
   - If `!time.Now().Before(leaf.NotAfter)`, the agent logs a structured `ERROR` message:
     `local mTLS client certificate expired (notAfter=..., serial=...); re-enroll required`
     and surfaces this exact reason instead of letting gRPC mask the TLS alert behind `context deadline exceeded`.
   - If the remote gateway rejects `RenewCertificate` with `PERMISSION_DENIED` (`certificate_expired` or `certificate_revoked`), the renewal manager logs the explicit re-enrollment diagnostic and halts further renewal retries.
2. **Gateway-side TLS alert logging (`elixir/serviceradar_agent_gateway`)**:
   - Configure the gateway TLS listener / handshake telemetry hook to log peer certificate CN, serial number, `notAfter`, and failure reason (`certificate_expired`, `certificate_revoked`, `unknown_ca`) whenever a client TLS handshake fails.

## Decision 5: Interaction with Leaf and Component Revocation (`#5257`)

`#5257` tracks edge NATS leaf and component certificate revocation. Phase 2 (`#6120`) implements predecessor-successor tracking in `ServiceRadarAgentGateway.AgentCertificateRevocation` and retires the predecessor (`reason = "superseded_by_renewal"`) only when the agent completes `Hello` presenting the successor certificate; durable CNPG revocation storage (`platform.revoked_component_certificates`) and NATS leaf auth callout remain deferred to `#5257` (tasks `2.1b` and `2.3`). Currently:
- `ServiceRadarAgentGateway.AgentCertificateRevocation` is an in-memory ETS table local to a single `agent-gateway` pod (lost on pod restart and not shared across gateway replicas).
- Edge NATS leaves share a partition-scoped URI SAN (`spiffe://serviceradar.local/nats-leaf/<partition_id>`), so revoking one compromised leaf certificate without durable fingerprint/serial revocation or per-leaf identity cannot isolate a single leaf.

### Unified Revocation & Renewal Integration
1. **Durable CNPG Revocation Store (`platform.revoked_component_certificates`, deferred to `#5257` tasks `2.1b`/`2.3`)**:
   - Create `platform.revoked_component_certificates` storing:
     - `id` (UUID PK)
     - `component_id` (`TEXT`, indexed)
     - `partition_id` (`TEXT`)
     - `component_type` (`TEXT`: `agent`, `addon`, `nats_leaf`, `checker`)
     - `serial_number` (`TEXT`, indexed)
     - `fingerprint_sha256` (`TEXT`, unique index)
     - `reason` (`TEXT`: `superseded_by_renewal`, `admin_revoked`, `decommissioned`, `re_enrolled`, `key_compromise`)
     - `revoked_at` (`TIMESTAMPTZ`)
     - `revoked_by` (`TEXT`)
     - `expires_at` (`TIMESTAMPTZ` -- `notAfter` of the revoked cert, allowing automatic pruning of revocation entries once the underlying certificate has naturally expired).
2. **Cluster-Wide Gateway Synchronization (`#5257` task `2.3`)**:
   - `ServiceRadarAgentGateway.AgentCertificateRevocation` loads active (non-expired) revocation rows from CNPG on startup and subscribes to PubSub (`serviceradar:cert_revocations`) so any revocation takes effect across all `agent-gateway` pods within milliseconds and survives pod restarts.
3. **Validity and Revocation Checks Before Renewal**:
   - Every `RenewCertificate` attempt enforces the current-time peer validity check in Decision 1 immediately before signing, including retries over existing connections.
   - `RenewCertificate` calls `ComponentIdentityResolver.resolve_from_cert/2`, which queries `AgentCertificateRevocation.revoked?/1` by `component_id`, `serial_number`, and `certificate_fingerprint`.
   - A revoked certificate or revoked `component_id` is immediately denied renewal (`PERMISSION_DENIED`).
4. **Predecessor Certificate Retirement on Renewal**:
   - When `RenewCertificate` issues a new certificate $C_{\text{new}}$ to replace $C_{\text{old}}$, `ServiceRadarAgentGateway.AgentCertificateRevocation.register_pending_renewal/3` records the predecessor-successor relationship for retirement upon confirmed successor use. Issuance starts no retirement timer; a lost response leaves the still-valid predecessor usable for retry.
   - As soon as the agent completes `Hello` presenting $C_{\text{new}}$, `AgentCertificateRevocation.confirm_successor_hello/1` retires $C_{\text{old}}$ by fingerprint in `AgentCertificateRevocation` with `reason = "superseded_by_renewal"`. It does not insert a serial-wide revocation: legacy issuance reused serial numbers across unrelated certificates. Durable storage remains deferred to `#5257`.
5. **Alignment with `#5257` Edge NATS Leaf Certificates**:
   - Per-leaf certificates issued for edge NATS leaves include a distinct `component_id` in their CN (`<leaf_component_id>.<partition_id>.serviceradar`) and URI SAN (`spiffe://serviceradar.local/nats-leaf/<partition_id>/<leaf_component_id>`), and consult the same `platform.revoked_component_certificates` store during TLS verification / NATS auth callout.

## Decision 6: Migration Plan for Field Agents with Near-Expiry or Expired Certificates

Agents already deployed in the field fall into three cohorts when this change ships:

1. **Cohort 1 -- Agents with valid certificates (`notAfter > now`) that upgrade to the new agent version before expiry**:
   - As soon as the agent upgrades (via the in-band `agent-gateway` release rollout or OS package upgrade), the gateway derives its current `cert_not_after` from the TLS peer certificate on `Hello`.
   - Certificates already due under the renewal schedule in Decision 1 trigger renewal once connected. A 1-day certificate is not necessarily due merely because its total lifetime is short; certificates not yet due follow that schedule. Successful renewal replaces the certificate with one using the configured deployment lifetime.
2. **Cohort 2 -- Connected agents still running an older binary (`< renewal-capable version`) whose certificate is approaching expiry**:
   - On first `Hello` after the gateway upgrades, `serviceradar-agent-gateway` inspects the peer TLS certificate's `notAfter` directly from the TLS socket and populates `ocsf_agents.cert_expires_at`.
   - Operators can immediately query `in:agents cert_expires_at:<7d` in SRQL and prioritize rolling the agent release update to those hosts before `notAfter` arrives.
3. **Cohort 3 -- Agents whose 1-day (or older) certificate has already expired (`notAfter <= now`)**:
   - Expired certificates cannot complete the mTLS handshake (Decision 2). These agents appear offline; `cert_expires_at < now` identifies them only if the gateway recorded their certificate metadata before expiry. Agents that expired before metadata collection began retain an unknown expiry and will not match that filter. Operators identify those certificates on the host via the new startup check or `openssl x509 -enddate -noout -in /etc/serviceradar/certs/component.pem`.
   - Operators use the **Re-enroll Agent** action (`POST /api/admin/agents/:uid/reissue-enrollment-token` or UI button) and run `sudo serviceradar-cli enroll --token <token>` (or an Ansible playbook across affected hosts) to install a fresh certificate under the [shared lifetime policy](../../../docs/docs/edge-agent-onboarding.md#certificate-lifetime-and-expiry-alerts) while preserving the existing `agent_uid`.

## Decision 7: Zero Dependency on SPIFFE/SPIRE

Per `#5413`, SPIRE is removed from ServiceRadar. This design has **no dependency** on SPIRE Server, SPIRE Agent, the Workload API, or `spire.spiffe.io` CRDs:
- The URI SAN `spiffe://serviceradar.local/<component_type>/<partition_id>/<component_id>` is retained purely as an internal X.509 URI SAN convention minted by `ServiceRadarAgentGateway.CertIssuer` and parsed by `ServiceRadarAgentGateway.ComponentIdentityResolver`.
- CSR verification uses Elixir `:public_key` / `:crypto`, issuance invokes OpenSSL, and the agent uses Go `crypto/tls` and `crypto/x509`. Current revocation storage and the planned durable backend are described in Decision 5.
