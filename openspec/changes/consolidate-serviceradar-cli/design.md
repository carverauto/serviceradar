# Design: Consolidate the two `serviceradar-cli` tools

## Context

Two binaries answer to `serviceradar-cli`:

- The **Go** tool (`go/cmd/cli`, shipped in `.deb`/`.rpm` + Bazel image
  graph) — install/ops surface, static cross-platform binary.
- The **JS** tool (`@carverauto/serviceradar-cli`, Node + Vite) — the
  dashboard-SDK authoring surface, and the far richer one.

Issue #4666 asked to "port the JS to Go." The honest constraint: the JS
tool's `dashboard build`/`dev` commands run Vite +
`@vitejs/plugin-react` to bundle an author's **React/TSX renderer** into
an ES module. That is not portable to Go. Everything else in the JS tool
(`auth`, `publish`, `validate`, `manifest`, `import`, `doctor`, `init`)
is orchestration and *is* portable — but the highest-value,
lowest-risk slice is authentication, because that is the thing an
operator needs and the thing the npm gate most gets in the way of.

So this change does the minimum that removes both pain points:
1. Rename the JS tool so `serviceradar-cli` names exactly one binary.
2. Port device-code auth into the Go binary, sharing the credential store.

## Goals / Non-Goals

**Goals**
- One canonical `serviceradar-cli` (the Go binary).
- Native, npm-free `auth login/status/logout` on Go.
- Bit-for-bit credential-store interop between the two tools.

**Non-Goals**
- Porting `build`/`dev` (React/Vite bundling) — stays JS.
- Porting `publish` in this change (uploads a JS-produced artifact).
- PKCE `--web` flow on Go (server-side follow-up; device-code only).
- Any change to the existing Go ops subcommands.

## Decisions

### D1: Rename the JS tool, keep the Go binary name
`serviceradar-cli` continues to name the Go binary (it is the one in the
OS packages and image graph — renaming *that* would be far more
disruptive). The JS package becomes `@carverauto/serviceradar-dashboard`
with a single `serviceradar-dashboard` bin. This matches what the JS tool
*is* (its second bin was already `serviceradar-dashboard`) and the
`add-cli-dashboard-publish-api` / `add-cli-device-auth` framing where the
JS tool is the "dashboard authoring loop."

### D2: Credential store is the interop contract, ported verbatim
The Go store MUST produce and consume files identical to
`js/cli/src/auth/credentials.ts`:
- Path: `$XDG_CONFIG_HOME/serviceradar/credentials.json` ->
  `~/.config/serviceradar/credentials.json`; Windows
  `%APPDATA%\serviceradar\credentials.json`.
- Mode `0600`; refuse group/world-writable parent on non-Windows.
- Schema `{"version":1,"instances":{"<url>":{"token","user?",
  "obtained_at?","expires_at?"}}}`.
- URL normalization = trim trailing slashes.
- Token resolution precedence: `--token` -> `SERVICERADAR_TOKEN` ->
  stored.

A dedicated test loads a fixture `credentials.json` generated by the JS
tool and asserts the Go reader parses it unchanged, and that a Go-written
file matches the JS writer's shape (2-space JSON is not required for
interop since the JS reader is `JSON.parse`; we still pretty-print for
human editing parity).

### D3: Device-code wire contract mirrors the JS client exactly
Endpoints, request bodies, and polling semantics are copied from
`js/cli/src/auth/login.ts` so both clients behave identically against the
`add-cli-device-auth` server:
- Device: `POST /api/v1/cli/auth/device` `{client_id:"serviceradar-cli",
  scope}`; read `verification_uri_complete||verification_uri`,
  `user_code`, `device_code`, `interval` (min 1s), `expires_in`
  (min 60s).
- Token: `POST /api/v1/cli/auth/token`
  `{grant_type:"urn:...:device_code", device_code}`.
- RFC 8628 §3.5 mapping on HTTP 400 `error`: `authorization_pending` ->
  continue; `slow_down` -> interval += 5s; `access_denied` /
  `expired_token` -> terminal. Legacy status fallbacks 428/425 ->
  continue, 410 -> expired, 403 -> denied (kept for older/proxied
  instances).
- 404 on the device endpoint -> manual-token fallback.

### D4: No new heavyweight dependency on the Go side
Device-code polling is `net/http` + `encoding/json` + `time`. Browser
open reuses an existing helper if the Go tree already has one; otherwise
a small `open`/`xdg-open`/`rundll32 url.dll,FileProtocolHandler`
shim. This keeps the ops binary lean and its build graph unchanged apart
from the new files.

## Risks / Trade-offs

- **Split brain persists** — dashboard authors still need Node for
  `build`/`dev`. Accepted: that work is inherently JS, and the operator
  auth path is now Node-free, which is the actual #4666 pain.
- **Rename breaks existing npm installs** of `@carverauto/serviceradar-cli`.
  Mitigated by a version bump + CHANGELOG deprecation note and the
  transitional-alias Open Question below.
- **Credential-schema drift** between the two tools would silently break
  interop. Mitigated by the JS-interop fixture test; any schema change
  must update both sides in lockstep (call this out in both files).

## Open Questions

1. **Transitional alias for the renamed npm package?** Publish a
   deprecated `@carverauto/serviceradar-cli` that re-exports/points at
   `@carverauto/serviceradar-dashboard` for one release, or hard-cut with
   only a CHANGELOG note? (Leaning: deprecate-and-point for one minor.)
2. **Do we also port `dashboard publish` to Go later?** The artifact is
   JS-produced, but an operator publishing a pre-built `dist/` from Go is
   plausible. Out of scope here; revisit once the build-artifact contract
   is frozen by `add-cli-dashboard-publish-api`.
3. **Scope default.** JS defaults `scope` to `dashboard.publish`. For a
   general-purpose ops CLI, is a broader/empty default more appropriate,
   or do we keep `dashboard.publish` for parity until other scopes exist?
