# Change: Restore anomaly alerting and surfacing (post-overhaul operability audit)

## Why

A full audit of the anomaly engine and capacity planner on demo (2026-07-12, v1.4.13) found that **detection is healthy but nothing reaches the user**. The edge addon (v0.2.0, 12 agents) emits ~1.2k–2.6k anomaly open/clear transitions per day into `platform.ocsf_events` (continuously since 2026-07-05), and the EventWriter consumer runs at zero lag — yet anomaly alerts have been dead since **2026-06-30 03:00 UTC**, device-page anomaly panels are structurally empty, seasonal/drift detection (formerly 91.5% of volume) has never produced a finding, and capacity forecasting silently stopped covering cpu/interface/flow on **2026-07-05 05:41 UTC**. Every failure is a deployment/wiring defect around the (correctly implemented) `overhaul-anomaly-engine-reliability` code, plus monitoring that only alarms on over-emission, never on silence. All findings below were adversarially re-verified against origin/staging v1.4.13 and live demo state; none has a fix merged or in flight.

Root-cause inventory (each independently sufficient to hide anomalies from users):

1. **Two-runtime.exs drift (P0).** The deployed release is built from `elixir/serviceradar_core_elx`, whose `config/runtime.exs` never received the anomaly Oban cron entries that exist only in `elixir/serviceradar_core/config/runtime.exs` (a path dep whose config Mix never evaluates for the release). Five workers are therefore **never scheduled in any production deployment**: `AnomalyEpisodeStaleCloseWorker`, `ResolveStaleAnomaliesWorker`, `SeasonalDisposition.Worker`, `SeasonalDisposition.EdgeBaselineProducer`, `AnomalyAddonConfigProjector`. Verified in-pod: live Oban crontab lacks all five; `platform.seasonal_disposition_states` has 0 rows ever; zero of 3 profiles / 52 assignments carry a `seasonal_baselines` key (the producer always writes the key on success — it has never completed). Because every drift-capable metric class defaults to `deseasonalized_only`, no baselines ⇒ **the entire CUSUM drift detector and seasonal signal are inert fleet-wide**.
2. **Stale alert-rule rows (P0).** The DB-stored `causal_prediction_health_finding` / `causal_capacity_health_finding` rules on demo (updated 2026-06-13/22) still match `subject_prefix "signals.causal.predictions"`, but findings arrive on `signals.analytics.predictions.*` since the #4319 cutover. `RuleSeeder` is insert-if-absent; migration `20260628224553` fixed `signal_type` on existing rows but overlooked `subject_prefix`. Proven live: `RuleMatcher.rule_matches_event?(real_open_finding, stored_rule) == false`; all rule-state rows have `last_seen_at <= 2026-06-30 03:00:32`. **Anomaly AND capacity alerts dead since then.**
3. **Alert-engine shard placement lottery (P0).** `StatefulAlertEngine`'s 8 Horde shards place onto any cluster member; `serviceradar_agent_gateway` never opts out of hosting distributed processes (web-ng does, `config.exs:153`) and runs with `repo_enabled: false`, where `load_rules` silently returns `[]` forever. Observed live: shard 7 (owns the anomaly rule) and shard 5 (falco) on gateway nodes with `rules_count=0`. Even with fixed rules, whether any alert rule is evaluated is a per-restart lottery (~9 members, 3 with a Repo).
4. **Episode write-off/read-on mismatch (P0).** `AnomalyEpisodeRegistry` (sole writer of `platform.anomaly_episodes`) defaults OFF via `EVENT_WRITER_ANOMALY_EPISODES`, set nowhere in helm/compose/runtime.exs; the table has 0 rows ever. web-ng's device anomaly panel defaults to the `:ash` episode source with no fallback — **device pages structurally show zero anomalies** while 16k+ findings sit in `ocsf_events`. (Overhaul task 2.12's "default on for demo after soak" was never realized in code or deploy config.)
5. **Capacity sources unreachable (P1).** `bf13097a0` restricted default forecast sources to `memory_usage`+`disk_usage`; the opt-in (`:default_source_opt_ins`) has **no setter anywhere** — no env, no DB field, no Settings UI. cpu/interface/flow forecasts stopped at the v1.4.6 roll and cannot be re-enabled in production. Remaining disk/memory rows are ~100% `skipped` (invisible on every surface, which filter `status:projected has_exhaustion:true`; `at_risk`/`exhaustion_projected` query tokens are phantoms excluded by a DB CHECK). Capacity OCSF findings stopped 2026-07-05 04:41.
6. **Silence is unmonitored (P1).** The only rate tripwire fires on over-emission. `AnomalyAlertLivenessCheck` — built to catch exactly defects 2 and 3 ("a silent rule-shape or signal rename regression must fail the rollout") and which already detects the stale subject_prefix — exists only as a manual mix task, wired into nothing.
7. **Latent traps (P2).** Episode heartbeat interval (1800s) equals the stale-close threshold (30 min) with zero jitter margin; the ingest existing-id dedupe + same-id heartbeats mean the alert engine never sees ongoing-open evidence, so once `ResolveStaleAnomaliesWorker` is actually scheduled (fix 1) it would auto-resolve genuinely-open long-lived anomalies after 6h with no re-fire; config seeders are create-only so post-first-boot env tuning is inert (and helm seeds `{}` overrides even on fresh installs, discarding code drift_mode defaults); two enabled anomaly profiles (n_sigma 3.0/5 vs 4.0/8) are simultaneously assigned to every agent with ambiguous precedence; the NATS `events` stream MaxAge of 30m discards verdicts during any core outage longer than that; the anomaly-detection spec still carries ~10 requirements for the deleted central DeepCausality reasoner, and the capacity-forecasting spec still mandates cpu/interface forecasting that shipped code excludes by default.

The observed UX — a single SNMP packet-counter anomaly that appeared then cleared — is the healthy remainder: the rolling z-score spike detector on ~20 SNMP counter series from 2 agents, emitting one open + one clear per episode (5–9 min lifetimes), read through the one surface (`Observability → Health`) that still queries raw events.

8. **Flap rate exceeds the overhaul's own soak gate (P1).** No central "real or not" disposition applies to these findings today: seasonal-disposition suppression never runs (defect 1) and only consults cpu/memory classes; the episode registry that folds churn is off (defect 4); the disposition reporter is report-only. The surviving ~20 SNMP counter series flap at ~50–120 rows/day each (marginal z≈3.0 crossings re-opening at the 600s reopen-cooldown ceiling) against the documented gate of ≤20 rows/series/day. Volume control is restored by this change's own fixes (episodes fold churn; projector makes central n_sigma/confirm tuning reach the edge; baselines eventually deseasonalize the counters) plus overhaul task 0.3's damping decision — but the post-fix soak MUST re-verify the per-series row bound.

## What Changes

**P0 — restore user-visible anomalies and alerts**

- Port the five missing anomaly cron entries (with their existing env gates) into `elixir/serviceradar_core_elx/config/runtime.exs`, and add a drift guard test asserting the release crontab contains every production-required worker so the two config trees cannot silently diverge again.
- Data migration rewriting `subject_prefix` `"signals.causal.predictions"` → `"signals.analytics.predictions"` in `match` and `recovery` of existing `stateful_alert_rules` rows (idempotent `jsonb_set`, cloning the `20260628224553` pattern), and make `RuleSeeder` reconcile managed seeded rules on contract drift instead of insert-if-absent-forever.
- `serviceradar_agent_gateway` opts out of hosting distributed processes (`host_distributed_processes: false`, mirroring web-ng); `StatefulAlertEngine.load_rules` logs loudly and emits telemetry when a shard has no Repo instead of silently evaluating zero rules.
- Enable the anomaly episode pipeline by default: `AnomalyEpisodeRegistry.enabled?` defaults **true** (env var becomes a kill switch), widen the stale-close threshold to ≥2× the episode heartbeat interval, and align the web-ng legacy events path's cpu-row filter with the episode path's default disposition so cpu findings are not unconditionally hidden.

**P1 — keep the pipeline observably alive**

- Schedule `AnomalyAlertLivenessCheck` as a recurring coordinator job whose failure raises an operational alert, and run the mix task as a release/rollout gate (overhaul task 6.7 owns the one-time demo execution; this change owns the permanent wiring).
- Add silence tripwires: alert when anomaly upserts are zero for N hours while metric ingest is alive, and when seasonal-baseline delivery has not completed recently (fleet-wide `seasonal_baselines` key freshness), surfacing `drift_inactive_no_baseline` so bounded silence is visible instead of indistinguishable from breakage.
- Make capacity source opt-in reachable: env (`SERVICERADAR_CAPACITY_FORECASTING_SOURCE_OPT_INS`) in both runtime.exs trees, a `default_source_opt_ins` field on `CapacityForecastConfig` + Settings UI, served through `AnomalyConfigRuntime`. Remove phantom statuses from shipped SRQL queries and give operators a way to see skip reasons.
- Judge alert staleness against episode liveness: `ResolveStaleAnomaliesWorker` SHALL NOT resolve an alert whose finding's episode is still open/heartbeating (fixes the dedupe-starvation trap before the 6h sweep is first scheduled).

**P2 — hardening and debt**

- Config seeder correctness: seed code-default `metric_class_overrides` when helm provides `{}`/absent; document that singletons are operator-owned after first boot; demo runbook item to refresh the 2026-06-13-era rows.
- Enforce a single enabled anomaly addon profile per fleet (validation + deterministic precedence + surfaced warning on duplicates). Demo cleanup of the duplicate enabled profile/assignments stays with overhaul task 0.3.
- Raise retention for `signals.analytics.predictions.>` (dedicated stream or longer MaxAge) so verdicts survive core outages >30m, and realign the stale `falco_events` registration to the provisioned `events` / `falco.logs` path.
- Remove the legacy `ATTRIBUTED_FLOW` EventWriter registration and any verified-empty orphan durable/stream. `flow.attributed.>` was a retired demo-canary route with no production publisher or supported consumer; it MUST remain unprovisioned. Current attribution stamps `event_type = "attributed_flow"` on the matching CNPG flow row and does not publish an attributed-flow NATS message.
- Do not treat `NETFLOW_RAW` or `SFLOW_RAW` as dead attributed-flow consumers. They are logical consumer names for the active raw subjects `flows.raw.netflow` and `flows.raw.sflow`; their stream placement, migration, and cleanup are owned by `scale-netflow-ingest-isolation`.
- Spec debt: remove the 10 dead central-reasoner requirements from the anomaly-detection spec; align the capacity-forecasting spec with monotone-consumable defaults + explicit opt-in; de-causal its naming. **BREAKING** (spec-level): cpu/interface capacity forecasting is opt-in, no longer mandated by default.

## Impact

- Affected specs: `anomaly-detection`, `capacity-forecasting`
- Affected code: `elixir/serviceradar_core_elx/config/runtime.exs`; `elixir/serviceradar_core/{priv/repo/migrations, lib/serviceradar/observability/{rule_seeder.ex, stateful_alert_engine*.ex, resolve_stale_anomalies_worker.ex, anomaly_episode_stale_close_worker.ex, anomaly_config_seeder.ex, capacity_forecasting/{worker.ex, source.ex}, anomaly_alert_liveness_check.ex}, lib/serviceradar/event_writer/processors/anomaly_episode_registry.ex}`; `elixir/serviceradar_agent_gateway/config`; `elixir/web-ng/lib/serviceradar_web_ng_web/live/{device_live/anomaly_capacity_data.ex, settings/anomaly_detection_live.ex, observability_health_live}`; `helm/serviceradar/templates/core.yaml`; NATS stream provisioning; `openspec/specs/{anomaly-detection,capacity-forecasting}`
- Relationship to the active `overhaul-anomaly-engine-reliability` change: this change does **not** duplicate it. The overhaul owns detector semantics, episode/emission design, and its still-open live gates (0.3 damping revert, 1.20.c scorecard, 4.5 interface-drift enablement, Phase 6 soaks/signed 0.2.0 package). This change owns the deployment/wiring defects that keep the overhaul's shipped code dormant in production, and the liveness monitoring that would have caught them.
- Relationship to the active `scale-netflow-ingest-isolation` change: that change exclusively owns the `NETFLOW_RAW` / `SFLOW_RAW` consumers, their concrete `flows.raw.*` subjects, and migration to the dedicated `flows` stream. This change only removes the unrelated retired `ATTRIBUTED_FLOW` registration and MUST NOT create, delete, or rehome raw-flow subjects.
- Demo expectation after P0 lands: device pages and alerts show the real (deliberately low-volume) stream — currently ~1–2 short-lived SNMP-counter episodes open at any instant across 12 devices; drift/seasonal findings begin only after baselines accumulate (≥3 weeks history per hour-of-week bucket for interfaces) and overhaul task 4.5 enables interface drift.
