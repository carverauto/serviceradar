# Proposal: remove flow events-drain consumers

## Problem

Every core start logs three warnings that all say the same thing: EventWriter
declares consumers against the shared `events` stream for subjects that no
longer live there.

- `SFLOW_RAW_EVENTS_DRAIN` / `NETFLOW_RAW_EVENTS_DRAIN`: best-effort drains
  generated by `maybe_append_events_drain_streams/1` (`stream_name: "events"`,
  subjects `flows.raw.sflow` / `flows.raw.netflow`). NATS resolves both
  subjects to the dedicated `flows` stream, validation refuses the fallback,
  and the drains skip. Observed on demo (build `sha-6a65d889a3`):

  `reason={..., {:unexpected_stream, [expected: "events", resolved: "flows"]}}`
- `ATTRIBUTED_FLOW` (release config only,
  `elixir/serviceradar_core_elx/config/runtime.exs`): declares
  `stream_name: "events"` for subject `flow.attributed.>`, which lives on the
  `attributed_flow` stream. The consumer falls back onto the discovered stream
  and binds, but every start logs:

  `Requested stream not matched by subject; using discovered stream`
  `requested_stream=events discovered_stream=attributed_flow subject=flow.attributed.>`
- Demo log evidence (read-only `kubectl logs`, 2026-11-12): exactly these
  three warnings at startup; every other EventWriter consumer binds cleanly,
  which bounds the audit below.

## What this changes

1. Delete the drain generator `maybe_append_events_drain_streams/1` and the
   `EVENT_WRITER_FLOW_DRAIN_EVENTS` kill-switch at the source. No
   `_EVENTS_DRAIN` consumer is ever declared again, so nothing is skipped
   silently and the two skip warnings disappear.
2. Delete the legacy `ATTRIBUTED_FLOW` registration from the release runtime
   config. `flow.attributed.>` was a retired demo-canary route with no
   production publisher and no supported consumer: nothing in this repository
   publishes it (the agent-side attribution path now travels over the edge
   spool), the `stream-flow-attribution-via-ownership-index` ingest path is
   unimplemented (1/60 tasks), and 36 minutes of demo core logs show zero
   attributed-flow processing past the consumer bind. This completes
   `restore-anomaly-alerting-and-surfacing` task 8.3a; that change ticks the
   box, this change does the work.
3. Add regression guards: `load_flow()` emits no best-effort drain entries,
   and the release runtime config never provisions or consumes
   `flow.attributed.>`.

## What this does NOT change

- Live raw-flow consumers (`NETFLOW_RAW`, `SFLOW_RAW` on the `flows` stream),
  their subjects, demand domain, fencing, and StarRocks persistence: untouched.
  Their placement, migration, and cleanup stay owned by
  `scale-netflow-ingest-isolation`.
- Server-side orphan durables and the `attributed_flow` stream itself:
  deletion stays an ops step alongside `scale-netflow-ingest-isolation` 6.3
  (drain and delete obsolete netflow durables on `events`). This change stops
  declaring the consumers; it deletes no server-side state and drops no
  messages.
- The generic `best_effort` producer/reconciler machinery: it remains the
  documented contract for any future backlog reader. Only its last users go
  away.
- The `Flows` processor's `flow.attributed.<partition>` decode branch: kept
  as a defensive decode path. It provisions nothing.

## Audit: no other consumer makes the same stream assumption

Enumerated every stream entry in `Config.default_streams/0`,
`Config.default_flow_streams/0`, `serviceradar_core/config/runtime.exs`, and
`serviceradar_core_elx/config/runtime.exs`, and compared each
`(stream_name, subject)` pair against the owning stream. Cross-checked with
the demo startup log: every other consumer (`EVENTS`, `PDNS_OCSF`, `FALCO`,
`TRIVY`, `K8S_INVENTORY`, `OTEL_*`, `LOGS`, `METRICS`, `BMP/SIEM_CAUSAL`,
edge-record family, exposure family, live raw flows) binds on its declared
stream with no warning. `EVENT_WRITER_FLOW_EXTRA_SUBJECTS` is unset on demo,
and Helm only renders it for concrete `flows.raw.*` leaves, so no extension
subject can reintroduce the pattern. The three warnings above are the whole
set.

## Rollout safety

Residual `flows.raw.*` messages can only still sit on `events` if that stream
owned the subjects within its MaxAge window (24h fallback shape): any
deployment that has run a drain-capable build drains them first, and any
older residual has aged out. The kill-switch already let operators disable
the drains (`EVENT_WRITER_FLOW_DRAIN_EVENTS=false`); removal makes that
permanent. Skip-version upgrades from pre-cutover builds accept at most the
already-aging trailing window, stated here so it is a decision, not an
accident.
