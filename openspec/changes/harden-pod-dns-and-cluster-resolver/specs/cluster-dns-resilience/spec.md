## ADDED Requirements

### Requirement: Bounded Pod DNS Resolver Defaults Across Helm Workloads
The `helm/serviceradar` and `helm/serviceradar-k8s-edge` charts SHALL render fixed pod `dnsConfig` options (`ndots: "2"`, `timeout: "2"`, `attempts: "2"`, and `single-request-reopen`) unconditionally on every chart-managed Deployment, StatefulSet, and Job pod template without requiring an operator-supplied Helm switch, and without increasing application client connect timeouts.

#### Scenario: Default chart install renders bounded pod dnsConfig on all workloads
- **GIVEN** `helm template` is rendered for `helm/serviceradar` and `helm/serviceradar-k8s-edge` with default `values.yaml`
- **WHEN** the rendered Deployment, StatefulSet, and Job pod specs are inspected
- **THEN** every pod spec SHALL include `dnsConfig.options` with `ndots="2"`, `timeout="2"`, `attempts="2"`, and `single-request-reopen`

#### Scenario: Single UDP DNS packet loss recovers within 5-second client connect budget
- **GIVEN** a ServiceRadar workload pod configured with the chart's fixed `dnsConfig`
- **WHEN** the initial UDP DNS query is dropped once in transit
- **THEN** the stub resolver SHALL reopen the socket and retry after 2 seconds so name resolution and TCP connection establishment complete within a 5-second caller connect budget

### Requirement: Explicit Cluster-Local Service FQDNs and Leaf Certificate SAN Parity
Intra-cluster Service endpoints rendered by `helm/serviceradar` SHALL default to 4-dot `<service>.<namespace>.svc.cluster.local` FQDNs so `ndots: "2"` resolves them on the first lookup without search-domain `NXDOMAIN` amplification, and internal mTLS leaf certificates generated by `generate-certs.sh` SHALL include `DNS:<service>.<namespace>.svc.cluster.local` in `subjectAltName` for every TLS-serving workload.

#### Scenario: Rendered service endpoints use 4-dot cluster FQDNs
- **GIVEN** `helm template` is rendered for `helm/serviceradar` in namespace `sr-prod`
- **WHEN** intra-cluster service URLs and hostnames in rendered ConfigMaps, Jobs, and workload environments are inspected
- **THEN** intra-cluster service hostnames SHALL use `<service>.sr-prod.svc.cluster.local` (or `<service>.<target-namespace>.svc.cluster.local` for cross-namespace services)

#### Scenario: Generated internal TLS certificates match cluster-local FQDNs
- **GIVEN** `generate-certs.sh` renders leaf certificates for namespace `sr-prod`
- **WHEN** the `subjectAltName` extension of each internal service certificate (`nats`, `core`, `web`, `kv`, `agent`, `gateway`, `rperf-client`, `log-collector`, `flow-collector`, `bmp-collector`, `falcosidekick`, `trivy-sidecar`, `k8s-inventory`, `trapd`, and `tools`) is inspected
- **THEN** each certificate SHALL contain `DNS:<service>.sr-prod.svc.cluster.local` alongside its existing short names

### Requirement: Cluster Resolver Companion Architecture for Kubernetes Deployments
Production and demo Kubernetes clusters running ServiceRadar under `kube-proxy` IPVS SHALL pair the chart's pod `dnsConfig` with node-local DNS caching (`NodeLocal DNSCache` forwarding cache misses over TCP `:53`) and sized CoreDNS UDP receive buffers so pod DNS resolution does not depend on 30-second IPVS UDP conntrack flows or overflow CoreDNS pod socket buffers.

#### Scenario: Node-local cache bypasses IPVS UDP conntrack and eliminates CoreDNS receive-buffer drops
- **GIVEN** a Kubernetes cluster running `NodeLocal DNSCache` with TCP upstream forwarding to CoreDNS and chart pods carrying `serviceradar.podDnsConfig`
- **WHEN** workloads execute sustained concurrent dual-stack DNS lookups over a 24-hour window
- **THEN** CoreDNS pod-namespace `Udp: RcvbufErrors` SHALL remain at zero new increments
- **AND** healthy in-cluster service endpoints SHALL record zero `:nxdomain` resolution failures
