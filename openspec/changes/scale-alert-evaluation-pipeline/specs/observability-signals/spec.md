## MODIFIED Requirements

### Requirement: Stateful rules evaluate OCSF events
The system SHALL evaluate event-signal stateful alert rules against OCSF events generated by log promotion or direct event ingestion, and SHALL evaluate log-signal stateful alert rules against stored log records through the compiled rule index, without first promoting those records to events.

#### Scenario: OCSF event evaluation
- **GIVEN** a stateful rule targeting OCSF events
- **WHEN** promoted events exceed the configured threshold in the window
- **THEN** the system SHALL create an alert tied to the event stream

#### Scenario: Log rule evaluation without promotion
- **GIVEN** a stateful rule with `signal: log` matching `severity_text` "error", a threshold of 5 and a 10-minute window, grouped by device
- **WHEN** five matching synthetic log records from `host000007.example.com` are stored within ten minutes
- **THEN** the system SHALL create one alert for that device
- **AND** no OCSF event SHALL be stored for those records unless a promotion rule matches them

## REMOVED Requirements

### Requirement: Durable bounded alert evaluation admission
**Reason**: Described admission into the CNPG evaluation inbox with per-rule and pending byte budgets that refuse load. Refusal fails the source batch and, after `max_deliver`, loses the evaluation. The inbox is removed.
**Migration**: Replaced by `alert-evaluation` "Candidates use a fixed key space and a dynamic stream map" and "Evaluation backpressure is lag and never loss". Residual inbox rows are imported in order by the cutover ("Cutover from the CNPG inbox is ordered and complete").

### Requirement: Ordered replay-safe rule processing
**Reason**: Described per-rule ordering and replay safety through inbox positions, completion receipts and one transaction per occurrence.
**Migration**: Replaced by `alert-evaluation` "Evaluation state is deterministic and incrementally checkpointed", "Alert effects fire exactly once" and "Duplicate candidates are counted once". Ordering is per (rule, group key), whose candidates always share one virtual partition and block, including across stream moves; rule-wide operations (disable, delete, maintenance) are ordered markers on every block.

### Requirement: Evaluation survives shard startup conflicts
**Reason**: Described the advisory-lock evaluation fence of the removed inbox owner.
**Migration**: Replaced by `alert-evaluation` "Leased block ownership is fenced".

### Requirement: Alert evaluation telemetry uses JetStream
**Reason**: Described inbox queue depth, age and rejection metrics. The inbox no longer exists.
**Migration**: Replaced by `alert-evaluation` "Alert evaluation health and telemetry", which keeps JetStream publication and bounded labels.

### Requirement: Alert callers distinguish acceptance and completion
**Reason**: Described the inbox acceptance contract of `evaluate_logs/1`, `evaluate_events/1` and `evaluate_metrics/1`.
**Migration**: Acceptance is now a candidate publish acknowledgement ("Storage and routing complete before acknowledgement" in `telemetry-ingestion-capacity`). Completion-dependent callers keep waiting for the persisted alert. Maintenance keeps its synchronous count through `alert-evaluation` "Stale-anomaly maintenance keeps its synchronous count".
