
# [ADLR]: Continuous Integration on BuildBuddy (BB)     
* Date: Aug/10 2026
* Author: Marvin Hansen
* Contact: marvin.hansen@gmail.com

## Abstract   
   
Adding a Rust E2E integration test required a rework of the entire SR-repo-wide Bazel configuration, adding a new BB-based CI workflow, and configuring a remote cache for BB. And a new linker. However, full CI time dropped tenfold, with average build times hovering around 2-3 minutes. The initial Rust E2E test still needs to be migrated to the new CI system. 
   
## Driving Event   
   
When I started working on the Rust source tree on July/14, it became clear that the Bazel config needed several improvements, mainly to make the Rust code compile locally on macOS. While adding these improvements, I decided to consolidate and vendor all Rust dependencies, mainly because the consolidation reduces the total number of Rust crates built and the vendoring prevents re-downloads of dependencies in case of a cache miss. Once these improvements were applied, I implemented the DGraph client for Rust, which then necessitated end-to-end integration testing on BB. The prior GH-Action-based CI integration took between 30 and 40 minutes to complete. However, the prior Bazel and BB configuration was only partially working, which then resulted in a concentrated effort to rework the prior configuration and configure parallel integration testing via BB CI Workflows.

The work was officially concluded on August/10/2026 when the full Bazel CI workflow was repeatedly measured to complete within 3-5 minutes. 
   
## Process    

### Bazel build rectification 

The prior Bazel setup only configured parts of the repository; for example, the entire Golang source tree was built and tested with the go binary runner and didn’t even use Bazel. Once the Go source tree was fully integrated into Bazel, the Elixir source tree was next. Elixir required more effort because the Bazel rules for Erlang and Elixir were abandoned in 2024, with critical functionality such as package management missing. Next, the missing functionality was added and multiple bugs were fixed in rules_erlang and rules_elixir to make the Elixir source tree build with Bazel. 

### Reconfiguration of build targets 

The Elixir source tree was initially slow to build. As a result, multiple build targets were reconfigured, unnecessary dependencies were removed, and multiple other improvements were applied. This had some impact, but not as much as initially hoped. 

### Right-sizing the BB cluster 

A source code statistic revealed that the primary code base is about 6 million LoC, with another 14 million LoC as dependencies. For a total of about 20 million LoC, the BB cluster was undersized.
It was also discovered that the RBE load balancer had crashed months earlier, and as a result, all compile tasks were executed on one single node instead of all three available nodes. 
In response, the load balancer was reconfigured and restarted, and the RBE executors were right-sized to a maximum of 32 cores per pod, for a maximum of 96 cores in total. 
The total build time improved substantially afterward. 

Concurrently with the right-sizing of the cluster, the .bazelrc was reworked to eliminate unnecessary and conflicting flags and to add various performance improvements.

Next, the workflow pod was isolated into a designated Kubernetes pool, as recommended in the official BB documentation, and its memory request was increased to 64 GB to prevent out-of-memory issues. 

### Transferred all OCI images to the colocated Harbor 

Bazel caches container images, with the implication that a cache hit skips the image, but a cache miss re-downloads the image. The ongoing work on the BB CI workflow quickly exhausted the GHCR rate limit, and the build then stalled on throttled image downloads at dial-up modem speed. 
In response, all OCI images previously pulled from Docker Hub or GHCR were migrated to the Harbor registry, which is self-hosted in the same cluster. 
As a result, container image pulling is near-instant. 

### Removal of the legacy Gold linker

While inspecting the build log, I noticed a large number of warnings emitted by the Rust compiler about the deprecated Gold linker. 
An online search confirmed that the binutils project had indeed deprecated the Gold linker in early 2024, with an undated notice that the Gold linker will eventually no longer be distributed. 
However, the BB Bazel rules required to build on the BB cluster hard-coded the Gold linker, presumably because of flag compatibility with the Bazel C/C++ rules. 
In response, I forked the BB Bazel rules and wrote a patch to make the linker configurable, with Gold as the default and an option to replace the linker with a custom one. 
Next, the patched rules were added to the SR repo using the git override tag in bazel_deps, and the Gold linker was replaced with the modern LLD. The Rust project reported that LLD often linked twice as fast as Gold, and so made it the default linker in the nightly build. 

However, replacing the linker exposed a compile failure of a Rust sub-dependency that was using AWS-LC as its crypto provider. When AWS-LC was replaced with the more portable ring-rs crypto provider, the test still failed. It turned out that the crypto provider compile error overshadowed another configuration mistake that set Gold as the linker. Once the setting was removed, the target built.   

Next, an ill-configured MUSL statically linked Rust binary required reworking the toolchain resolution. The root cause is an ancient blunder in the Rust compiler: toolchains are separated by operating system (e.g., Linux) and platform (e.g., x86), but not by ABI (e.g., GNU), and as a result rules_rust often incorrectly selected LLVM instead of MUSL for the static binary target. This bug does not trigger on macOS because there is just one ABI. However, under Linux it does, and it may result in dynamically linked binaries despite an otherwise correct MUSL static configuration. 
The rework fixed the toolchain resolution, and afterward the MUSL binary was correctly linked statically. 
An adjacent libc version test started failing afterward. It is unclear whether the test failure was triggered by the reworked toolchain resolution or the replaced linker. However, it was decided to link those native add-on binaries statically because they are supposed to be distribution-independent and are easier to deploy when there is no libc requirement. 
 
### Removal of the legacy el9 profile and image 

A recurring CI job failure related to the native add-ons revealed that the legacy el9 Bazel profile and OCI image were still in use. This was exposed because the el9 image does not have the modern LLD linker installed, and some targets failed to compile. In response, the entire legacy el9 Bazel profile and OCI image were removed. Instead, the affected GH Action was migrated to use the modern CI profile with Bazel remote build. 

### Enabling Remote Cache CDC 

BuildBuddy's Remote Cache uses Content-Defined Chunking (CDC) to make large build outputs behave more incrementally. When a binary, bundle, package, or archive is mostly unchanged, BuildBuddy can reuse chunks it has already seen instead of re-uploading or re-downloading the entire file.

This feature was introduced on May 1, 2026, and after enabling the experimental_remote_cache_chunking flag, cache uploads dropped by about 75% on average per day. 

### Configuration of the Remote Cache Proxy 

Despite all prior efforts, the total CI workflow time on BB remained stuck at around 11 minutes. The linker replacement did improve build times by a few seconds, and the removal of AWS-LC cut almost a minute of build time, but further build time reduction through configuration stayed elusive. 

The Remote Cache Proxy had been deployed a few days earlier, but the correct configuration proved difficult. An inquiry in the BB support Slack confirmed that external cluster access is unnecessary for workflow caching, and that instead the connection between the workflow pod and the remote cache proxy needs a setting in the global .bazelrc file. That was true, but the full configuration required several more steps. Eventually, the Remote Cache Proxy was configured, and subsequent BB CI runs dropped to ~3 minutes when hitting the remote cache proxy.   
   
## Lesson(s) Learned   

1) Keeping the Bazel configuration for the entire repo well maintained precedes any work on remote execution and remote caching. 

2) The BB enterprise features such as self-hosted executors or the remote cache proxy are under-documented on purpose, to incentivize enterprise customers to talk to the BB sales team and get the one-day deployment blueprint. A valid business practice, and one without the need for license keys. And the math favors their argument, because spending a week on BB is a quarter of a monthly engineer's salary, which can already be more than the consulting fee. 

However, working around the “not supported outside an enterprise contract” constraint required pointing Claude at the cloned BB repo in an adjacent folder. This helped resolve the bulk of configuration issues by simply matching the Helm chart configuration values against the parsing and processing in the BB code. 

3) The Bazel rules for Elixir and Erlang are in an abysmal state and will require a major rework. Currently, they are vendored and patched in the third_party folder. As before, pointing Claude at the actual rule code and the target configuration was often the only way to compel Claude to take the task on at all, let alone produce a functional solution. 

4) The same pattern recurred with the MUSL static issue. However, even with the full code of rules_rust in an adjacent folder, Claude frequently still hit the wall and asked to give up... There is something intrinsically complex about toolchain debugging in Bazel. 

5) The increased inter-cluster connectivity, from the Harbor registry to BB workflows and executors, and now the cache proxy, puts increased pressure on the networking hardware. Worth considering 10 Gb/s networking or faster to push beyond the current limits. 
   
## Recommendation(s)   
   
1) Continuously maintain the Bazel configuration. 
2) Sanity-check AI edits. 
3) Leverage the new cache proxy in the daily development workflow for much faster velocity.
