
# [ADLR]: Continuous Integration on BuildBuddy (BB)     
* Date: Aug/10 2026
* Author: Marvin Hansen
* Contact: marvin.hansen@gmail.com

## Abstract   
   
Adding a Rust E2E integration test required a re-work on the entire SR repo wide Bazel configuration, adding a new BB based CI workflow, and configuring remote cache for BB. And a new linker. However, full CI time dropped tenfold with average build times hovering around 2-3 minutes. The initial Rust E2E test still needs to be migrated to the new CI system. 
   
## Driving Event   
   
When I started working on the Rust source tree on July/14, it became clear that the Bazel config needed several improvements mainly to make the Rust code compile locally on MacOS. While adding these improvements, I decided to consolidate and vendor all rust dependencies mainly because the consolidation reduces the total number of Rust crates build and the vending prevents re-downloads of dependencies in case of a cache miss. Once these improvements were applied, I implemented the DGraph client for Rust, which then necessitated end to end integration testing on BB. The prior GH action based CI integration took between 30 and 40 minutes to complete. However, the prior Bazel and BB configuration was only partially working, which then resulted in a concentrated effort to re-work the prior configuration and configure parallel integration testing via BB CI Workflows.

The work was officially concluded on August/10/2026 when the full Bazel CI workflow was repeatedly measured to complete within 3-5 minutes. 
   
## Process    

### Bazel Build rectification 

The prior Bazel only configured parts of the repository; for example the entire Golang source tree was build and tested with the go binary runner and didn’t even used Bazel. Once Go source tree was fully integrated into Bazel, the Elixir source tree was next. Elixir required more effort because the Bazel rules for Erlang and Elixir were abandoned in 2024 with critical functionality such as packages management missing. Next, the missing functionality and multiple bugs were fixed in rules Erlang and Elixir to make the Elixir source tree build with Bazel. 

### Reconfiguration of build targets 

The Elixir source tree was initially slow to build. As a result, multiple build targets were reconfigured, unnecessary dependencies were removed and multiple other improvements were applied. This had some impact, but not as much as initially hoped. 

### Right sizing the BB cluster 

A source code statistic revealed that the primary code base is sized about 6 mio LoC with another 14 min LoC as dependencies and for a total of about 20 mio LoC, the BB cluster was under-sized.
It was also discovered that the RBE load balanced had crashed months ago and as a result, all compile tasks were executed on one single node instead of all three available. 
In response, the load balancer was reconfigured, and restarted, and the RBE executors were right sized to a maximum of 32 cores per pod totaling 96 core as maximum. 
The total build time improved substantially afterwards. 

Concurrently to the right sizing of the cluster, the .bazelrc was re-worked to eliminate unnecessary flags, conflicting flags, and to add various performance improvements.

Next, the workflow pod was isolated into a designated Kubernetes pool, as recommended in the official BB documentation, and its memory request was increased to 64GB to prevent Out of Memory issues. 

### Transferred all OCI images to the colocated harbor 

Bazel caches container images with the implication that a cache it skips the image, but a cache miss re-downloads the image. The ongoing work on the BB CI workflow quickly exhausted the GHCR rate limit and thus the build stalled over throttled image download at dial-up modem speed. 
In response, all OCI images previously pulled from DockerHub or GHCR were migrated to the harbor registry which is self hosted in the same cluster. 
As a result, container image pulling is near instant. 

### Removal of the legacy Gold linker

While inspecting the build log, a large number of warnings emitted by the Rust compiler about the deprecated Gold linker were noticed. 
An online search confirmed that the binutils project indeed deprecated the gold linker in early 2024 with an undated notice that eventually the Gold linker will not be distributed any longer. 
However, the BB bazel rules required to build on the BB cluster hard coded the gold linker presumably because of flag compatibility with the Bazel C/C++ rules. 
In response, I forked the BB Bazel rules, wrote a patch to make the linker configurable with Gold as the default and an option to replace the linker with a custom one. 
Next, the patched rules were added to the SR repo using the git overwrite tag in bazel_deps and the gold linker was replaced with the modern LLD. The Rust project reported that LLD oftentimes linked twice as fast as gold, and thus they made it the default linker in the nightly build. 

However, replacing the linker exposed a compile failure of a Rust sub-dependency that was using AWS-LC as crypto provider. When AWS-LC was replaced with the more portable ring-rs crypto provider, the test was still failing. It turned out, the crypto provide compile error overshadowed another configuration mistake that set GOLD as a linker. Once the setting was removed, the target build.   

Next, an ill configured MUSL static linked Rust binary required re-working the toolchain resolution. The root cause is an ancient blunder in the Rust compiler that toolchains were separated by Operating System (e.g. Linux), and platform (e.g. x86), but not by ABI (e.g. Gnu) and as a result rules_rust oftentimes incorrectly selected LLVM instead of MUSl for the static binary target. This bug does not trigger on MacOS because there is just one ABI. However, under Linux it does and it may results to dynamically linked binaries despite an otherwise correct MUSL static configuration. 
The re-worked fixed the toolchain resolution and afterwards, the MUSL static binary was correctly linked statically. 
An adjacent libc version test started failing afterwards. It is unclear if the test failure was triggered by the re-worked toolchain resolution or the replaced linker. However, it was decided to link those native addon binaries statically because they are supposed to be distribution independent and thus are easier to deploy when there is no libc requirement. 
 
### Removal of the legacy el9 profile and image 

A reoccurring CI job failure related to the native add-ons revealed that the legacy el9 Bazel profile and OCI image was still in use. This was exposed because the el9 image does not have the modern LLD linker installed and some targets failed to compile. In response, the entire  legacy el9 bazel profile and OCI image was removed. Instead, the affected GH action was migrated to use the modern CI profile with bazel remote build. 

###  Enabling Remote Cache CDC 

BuildBuddy's Remote Cache uses Content-Defined Chunking (CDC) to make large build outputs behave more incrementally. When a binary, bundle, package, or archive is mostly unchanged, BuildBuddy can reuse chunks it has already seen instead of re-uploading or re-downloading the entire file.

This feature was introduced May 1, 2026, and after enabling the experimental_remote_cache_chunking flag, cache upload dropped by about 75% on average per day. 

### Configuration of the Remote Cache Proxy 

Despite all prior efforts, the total CI workflow time on BB remained stale at around 11 minutes. The linker replacement did improved build times by a few seconds, the removal of AWS-LC removed almost a minute of build time, but further build time reduction by configuration stayed elusive. 

The Remote Cache Proxy was deployed a few days prior, but the correct configuration has proven difficult. An inquiry in the BB support slack confirmed that an external cluster access is unnecessary for workflow caching and instead the connection between the workflow pod and the remote cache proxy needs a setting in the global .bazelrc file. That was true, but the full configuration required several more steps. Eventually, the remote Cache Proxy was configured and subsequent BB Ci runs reduced to ~3 min when hitting the remote cache proxy.   
   
## Lesson(s) Learned   

1) Keeping the  Bazel configuration for the entire repo well maintained precedes any work on remote execution and remote cache. 

2) The BB enterprise features such as self hosted executors or the remote cache proxy are under documented by purpose to incentivizes enterprise customers to talk to the BB sales team to get the one day deployment blueprint. Valid business practice without the need for license keys. And the math favors their argument because spending a week on a BB is a quarter of a monthly engineers salary and that can already be more than the consulting fee. 

However, working around the “not supported outside an enterprise contact” constant required to point claude at the cloned BB repo in an adjacent folder. This helped to resolve the bulk of configuration issues by simply matching the helm chart configuration values against the parsing and processing in the BB code. 

3) The bazel rules for Elixir and Erlang are in an abysmal stage and will require a major rework. Currently, they are vendored and patched in the third_party folder. Similar to before, pointing claude at the actual rule code and the target configuration was often the only way to compel claude to even take the task on let alone produce a functional solution. 

4) The same pattern reoccurred with the MUSl static issue. However, even with the full code of rules_rust in an adjacent folder, Claude still hit frequently the wall and asked to give up... There is something intrinsically complex about toolchain debugging in Bazel. 

5) The increased inter-cluster connectivity, from the harbor registry, BB workflows to executers and now the cache proxy puts increased pressure on the networking hardware. Worth considering 10GB/s networking or faster to push beyond the current limits. 
   
## Recommendation(s)   
   
1) Continuously maintain the Bazel configuration. 
2) Sanity check Ai edits. 
3) Leverage the new cache proxy in the daily development workflow for much faster velocity.
