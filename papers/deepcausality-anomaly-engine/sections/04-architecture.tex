\section{Engine Architecture}
\label{sec:architecture}

The engine is two Rust crates. \texttt{anomaly-core} is the reasoner: the
statistics, the windowing, the signal evaluation, the detector flow, and the
shared types. \texttt{anomaly-addon} is the per-series engine and the add-on
runtime that wraps it. The split matters because the same reasoner core computes a
verdict wherever it runs, so two deployments of the core produce identical verdicts
for identical input. A parity test pins this property.

\subsection{The causal formulation}
Each series is watched by a causaloid evaluated over that series' recent window.
The reasoner entry point, \texttt{reason\_impl}, is a \texttt{CausalFlow} pipeline:
it hydrates the detector state from the supplied context, evaluates the signal,
branches on whether the sample breached, and finalizes a verdict. The pass is
stateless. It takes a context and a sample and returns a verdict together with the
next state to persist. Nothing about the reasoner is tied to where it runs, which
is what lets the same code serve as the per-agent detector.
\Cref{fig:causalflow} shows the pipeline. The arm that fires on a breach counts
toward the confirmation run, and the clean arm resets the run and admits the sample
to the window. That same \texttt{branch\_with} is where a future guarded
intervention would hook in, alongside or in place of emitting a verdict.

\begin{figure}[t]
\begin{lstlisting}
CausalFlow::process(state)          // seed the per-series state
    .context(thresholds)            // attach the read-only config
    .map(|_| EvaluateSample)
    .update_value_state_context(evaluate_detector)   // z-score the sample
    .branch_with(
        |v, _, _| breached(v),
        |breach| breach.update_state(|s| { s.consecutive += 1; s }),
        |clean|  clean.update_state(|s| { s.consecutive = 0; s.admit(); s }),
    )
    .update_value_state_context(finalize_verdict)
    .finish()
\end{lstlisting}

  simplified from \texttt{reason\_impl}. Each step lowers to a causal-monad
  operation; the breach branch confirms or resets, and the clean arm admits the
  sample to the baseline.}

\end{figure}

\subsection{The per-series engine}
\texttt{DetectorEngine} holds a bounded map from series key to a small per-series
state, plus a second map of the last counter reading per series for rate
normalization. It enforces a hard cap on the number of tracked series: a sample for
a new series past the cap is dropped and counted, while series already tracked keep
evaluating. Process metrics are filtered out before they reach the map. For each
incoming sample the engine rate-normalizes it if it is a counter, looks up or
creates the series state, runs the reasoner, persists the returned state, and
forwards a verdict when a sample breaches.

\subsection{Engine boundaries}
The engine's interface is narrow on purpose: a sample goes in, a verdict comes out.
Everything before the sample (how telemetry is collected and delivered to the
add-on) and everything after the verdict (how findings are transported, stored,
and alerted on) sits outside the engine and outside this paper. Holding that line
is what keeps the per-series cost, and therefore the edge footprint, small and
predictable.
